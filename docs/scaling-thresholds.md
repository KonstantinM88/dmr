# DMR — Scaling Thresholds

## 1. Принцип

Не масштабировать инфраструктуру заранее. Использовать существующий
Hostinger Business + текущий Neon plan, пока измерения не покажут
обратное. Расширение ресурсов Hostinger/Neon — только после нагрузочного
теста или подтверждённых эксплуатационных ограничений, и только с
отдельным разрешением владельца (никаких автоматических апгрейдов).

## 2. Обязательные проверки перед принятием решения о масштабировании

1. Production-like build.
2. Деплой на Hostinger Business.
3. Проверка connectivity к Neon.
4. Проверка Stripe webhook под нагрузкой.
5. Проверка SSE и polling fallback.
6. Нагрузочный тест: 100 одновременно активных гостевых сессий (чтение
   меню, создание OrderRound, подтверждение официантом, kitchen/bar
   updates, reconnect).
7. Нагрузочный тест waiter/kitchen/bar dashboards под той же нагрузкой.
8. Замер CPU/RAM/I/O/latency на Hostinger.
9. Замер connections/compute/network transfer на Neon.
10. Проверка загрузки изображений/видео через CDN/object storage.

## 3. Условия, при которых расширение считается обоснованным (одно или несколько)

- Hostinger CPU длительно ≥80% в часы пик.
- RAM регулярно исчерпывается.
- Появляются 503 или непредвиденные перезапуски процесса.
- Растёт очередь запросов.
- p95 latency критических order-эндпоинтов превышает согласованный
  бюджет (бюджет фиксируется в Этапе 1 при первых замерах).
- Stripe webhook обрабатывается нестабильно/с большой задержкой.
- Realtime-соединения регулярно обрываются.
- Polling fallback создаёт чрезмерную нагрузку.
- Next.js build перестаёт помещаться в лимиты Hostinger.
- Neon приближается к лимитам compute/storage/network transfer текущего
  плана.
- Neon connection pool регулярно исчерпывается.
- Нагрузочный тест на 100 пользователей не проходит критерии готовности.

Единичный кратковременный всплеск — недостаточное основание. Проблема
подтверждается повторным тестом или наблюдением в нескольких реальных
пиковых периодах.

## 4. Путь масштабирования (по порядку, каждый шаг — по отдельному согласованию)

1. Оптимизация запросов/индексов/кэширования/client bundle.
2. Оптимизация polling/SSE и media delivery.
3. Увеличение текущего Neon plan/compute.
4. Переход с Hostinger Business на Hostinger Cloud.
5. Переход на Hostinger VPS (если нужны Docker/Redis/workers/полный
   контроль realtime).
6. Выделение отдельных сервисов — только при доказанной необходимости.

## 5. Перед любой миграцией — обязательный отчёт владельцу с

измеренной проблемой, метриками, предполагаемой причиной, вариантами
решения, стоимостью и сложностью, риском downtime, планом миграции,
планом отката. Апгрейд никогда не выполняется автоматически.

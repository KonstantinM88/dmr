# Digital Menu Restaurant (DMR) — Product Spec

## 1. Назначение

Отдельное production-приложение: цифровое ресторанное меню по QR-коду на
столе, с корзиной на устройстве, подтверждением заказов официантом,
производственными очередями кухни и бара, дозаказами, онлайн-оплатой
(Stripe, MVP: весь оставшийся счёт) и ролевой staff/admin-панелью.

## 2. Гостевой сценарий (de, mobile-first)

1. Скан QR на столе → нейтральный URL без последовательного ID →
   определение стола по opaque token → сохранённый/дефолтный язык (de).
2. Гость видит номер стола и состояние текущей DiningSession, без
   регистрации, без персональных данных на этом этапе.
3. Категории → блюда/напитки → полная карточка (описание, состав,
   аллергены, добавки, dietary labels, острота, масса/объём, варианты,
   модификаторы, цена, availability, медиа).
4. Тап по изображению — короткое видео (muted/loop/playsInline), тап ещё
   раз — пауза; на desktop — hover-preview.
5. Выбор варианта/модификаторов/количества/комментария → добавление в
   персональную корзину устройства (переживает reload, привязана к
   Venue+столу+DiningSession).
6. Отправка первого заказа → статус «ожидает официанта» → после решения
   официанта — статусы приготовления по позициям (в очереди/принято/
   готовится/готово/подано).
7. Дозаказы в рамках той же DiningSession: по умолчанию тоже ждут
   официанта; если официант включил AUTO_ACCEPT для текущей сессии —
   дозаказ сразу уходит на нужную станцию, гость видит это состояние явно.
8. Запрос счёта → на MVP оплата только всего оставшегося счёта через
   Stripe (карта, Apple Pay/Google Pay если доступны) → результат
   подтверждается только сервером через Stripe webhook, не client redirect.
9. Несколько устройств за одним столом — отдельные анонимные участники
   (Participant/GuestDevice), общий счёт и общий статус сессии.

## 3. Staff-сценарии

- **WAITER**: видит назначенные столы, подтверждает/отклоняет OrderRound,
  создаёт ручной заказ, переключает `reorderApprovalMode` для текущей
  DiningSession (аудируется), отмечает подачу, запрашивает оплату,
  регистрирует разрешённые наличные/терминальные платежи (в MVP —
  функциональность только в модели данных, UI — Этап 5).
- **BARTENDER / CHEF**: видят только свою производственную очередь (bar/
  kitchen), принимают тикеты, меняют статус, отмечают готовность.
- **ADMIN**: меню, категории, цены, availability, столы/QR,
  operational-настройки, сотрудники в пределах разрешений; не удаляет
  финансовую историю.
- **ACCOUNTANT**: платежи, возвраты, налоговые разрезы, cash settlements,
  разрешённые экспорты, возвраты при наличии permission; без доступа к
  кухонной/барной очереди.
- **OWNER**: полный доступ, роли, критические настройки, Stripe metadata,
  аудит, отчёты, интеграции.

## 4. Зафиксированные бизнес-правила (не пересматриваются в Этапе 0)

- Локаль по умолчанию — de; сразу заложена расширяемость на en/ru/др.
- Первый заказ сессии всегда требует подтверждения официанта.
- Дозаказы по умолчанию тоже требуют подтверждения; официант может
  включить AUTO_ACCEPT только для текущей активной DiningSession — это
  не постоянная настройка физического стола, сбрасывается при закрытии
  сессии, каждое изменение аудируется (было/стало/кто/когда).
  AUTO_ACCEPT запрещён при `PAYMENT_PENDING/PAID/CLOSED/CANCELLED`.
- MVP-оплата: только Stripe, только весь оставшийся счёт; модель данных
  с первого дня допускает частичные/наличные/терминальные/смешанные
  оплаты (Этап 5, отдельная команда владельца).
- Не называть внутреннее payment confirmation фискальным чеком/Rechnung,
  пока не реализована сертифицированная кассовая/фискальная модель
  (KassenSichV/TSE/Belegausgabepflicht — отдельное юридическое
  исследование до production, см. `docs/payment-model.md` §6).
- Инфраструктура старта — существующие Hostinger Business + Neon, без
  покупки новых платных ресурсов без отдельного разрешения владельца.

## 5. Явные UI-состояния (обязательны, de-тексты)

loading, empty, sold out, offline, cart restored, price changed,
submission pending, awaiting waiter, accepted, partially accepted,
rejected, preparing, ready, served, waiter approval disabled/required for
reorders, payment pending/failed/succeeded, partially paid, paid, session
closed.

## 6. Критерий готовности MVP

См. полный список критериев в исходном ТЗ владельца — используется как
чек-лист приёмки Этапа 4 в `docs/implementation-plan.md`. Ключевые
проверяемые пункты: раздельные корзины устройств не смешиваются,
серверный пересчёт цены и идемпотентность отправки заказа, кухня/бар
получают только свои позиции, historical snapshots неизменны, staff
permissions проверяются на сервере, Stripe test-платеж закрывает весь
счёт и webhook идемпотентен, production build/lint/typecheck/tests/load
smoke проходят, есть Hostinger deployment/recovery документация.

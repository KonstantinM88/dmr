# DMR — Payment Model

## 1. Принцип

Раздельные сущности вместо одного поля `paid: boolean`: Bill/Check,
PaymentAttempt, Payment, PaymentAllocation, PaymentProviderEvent, Refund,
Tip, CashSettlement, FinancialAuditEvent (см. `data-model.md` §6).
Статус оплаты `DiningSession` всегда **вычисляется** из финансовых
записей и allocations.

## 2. Денежные расчёты

- Никогда не использовать JS floating point для денег.
- Integer minor units (центы) как основная стратегия хранения/расчёта;
  либо строго контролируемый `Decimal` — выбор фиксируется в Этапе 1 при
  первой реализации Prisma-схемы и не меняется впоследствии без миграции.
- Валюта по умолчанию — EUR.
- Налоговый профиль (`TaxProfile`) и tax snapshot — отдельно от цены;
  ставки настраиваемы и подтверждаются бухгалтером/владельцем, не
  захардкожены как вечные константы.

## 3. MVP Stripe (Этап 4) — обязательные правила

1. Сумма к оплате рассчитывается на сервере.
2. В сумму входят только принятые (`ACCEPTED`+) и ещё не оплаченные
   позиции.
3. Перед созданием PaymentIntent счёт (`Bill`) повторно пересчитывается
   на сервере.
4. `DiningSession` переходит в `PAYMENT_PENDING`.
5. Новые `OrderRound` временно запрещены (см. `order-state-machines.md`).
6. Client redirect после Stripe **не** считается подтверждением оплаты.
7. Источник истины — Stripe webhook (route handler с проверкой подписи).
8. `PaymentProviderEvent.providerEventId` уникален — защита от дублей.
9. Повторная доставка одного webhook-события не создаёт повторный
   `Payment`.
10. После успеха — создаются `Payment` + `PaymentAllocation` на все
    неоплаченные позиции счёта.
11. Все позиции счёта помечаются полностью распределёнными
    (`remainingAmount = 0`).
12. `DiningSession` переходит в `PAID`.
13. Закрытие сессии (`CLOSED`) — отдельное действие, не автоматическое
    при `PAID`.
14. Сбой оплаты (`FAILED`/`CANCELLED` PaymentAttempt) возвращает сессию в
    безопасное состояние (`OPEN`), позволяя повторную попытку или новый
    заказ.
15. Данные карты никогда не проходят через сервер приложения (Stripe
    Elements/Payment Element на клиенте, только `client_secret`
    передаётся с сервера).

MVP: один PaymentIntent на попытку, оплата только всего оставшегося
счёта. Test mode на этапе разработки. Apple Pay/Google Pay — если
доступны через выбранный Stripe-компонент без дополнительной интеграции.
Idempotency key на создание PaymentIntent (защита от дублирования при
повторном клике/retry). Reconciliation: read-only отчёт для бухгалтера,
сверяющий `Payment` с `PaymentProviderEvent`.

## 4. Будущие способы оплаты (модель данных готова, UI/flow — Этап 5, отдельная команда владельца)

Полный список: весь счёт Stripe/наличные/терминал; «каждый гость платит
своё»; выбор конкретных позиций; разделение позиции между несколькими
плательщиками; равный сплит; произвольная сумма; частичные и
последовательные платежи; смешанные Stripe+cash/Stripe+terminal;
несколько наличных платежей; чаевые; частичный/полный возврат.

`PaymentAllocation` с первого дня спроектирована так, чтобы предотвращать:
двойную оплату позиции, оплату сверх остатка, отрицательный остаток,
одновременное резервирование одной суммы двумя `PaymentAttempt`
(временное резервирование на время попытки + безопасное освобождение
просроченного резерва), закрытие счёта с неоплаченным остатком.

`orderedByParticipantId` на `OrderItem` — вспомогательная подсказка для
«моих позиций», не единственный источник истины; официант может
переносить/корректировать принадлежность позиции только через
аудируемую операцию (`FinancialAuditEvent`/`AuditLog`). Общее блюдо на
нескольких плательщиков — поддерживается будущим механизмом разбиения
line item на несколько allocation-целей.

## 5. Наличные и терминал (данные готовы в Этапе 1-4, UI — Этап 5)

Наличный платёж регистрирует только сотрудник с `REGISTER_CASH_PAYMENT`;
гость не может сам пометить счёт оплаченным. `CashSettlement` хранит
сумму, валюту, способ, полученную сумму, сдачу, оплачиваемые
позиции/долю, время, `staffUserId`, примечание. Терминальный платёж
подтверждается сотрудником либо интеграцией терминала (не определено на
Этапе 0). Все такие действия — в `AuditLog` и сменном отчёте.

## 6. Фискальные ограничения (Германия) — отдельное юридическое исследование до production

До production необходимо отдельно исследовать и задокументировать
применимость: KassenSichV, TSE, Belegausgabepflicht, VAT/Umsatzsteuer,
кассовая отчётность, требования к возвратам, возможная интеграция с
сертифицированной кассой/POS. **До реализации этой модели** приложение
не называет внутреннее payment confirmation фискальным чеком или
Rechnung — DMR на MVP работает как ordering/payment companion к
существующей кассе ресторана, не заменяет её. Это не блокирует Этапы
1-4, но блокирует заявления о «чеке» в UI-текстах и заявление о полной
фискальной готовности.

## 7. Тестовое покрытие (Этап 4+)

Unit: денежные расчёты (округление, integer minor units), PaymentAllocation
(over-allocation protection). Integration: Stripe webhook (валидный,
повторный, невалидная подпись), idempotency создания PaymentIntent.
Playwright: успешная полная оплата, неуспешная оплата, восстановление
сессии после сбоя.
